# USBeeKeeper v0.1.0

USBeeKeeper's first regular release brings USB inspection and a logical USB
topology tree to KDE Plasma 6. It promotes the functionality tested in the
Fedora COPR `0.1.0-dev.3` packages, including device details, detail-level
settings, optional renaming controls and package updates. This release does
not introduce a new hardware backend or claim complete hardware coverage.

## Install on Fedora KDE — recommended

Install and start **usbeehived separately**, then enable the USBeeKeeper COPR:

```bash
sudo dnf copr enable 2crazy4nick/usbeekeeper
sudo dnf install usbeekeeper
usbeekeeper-check-installation
```

The `usbeekeeper` RPM includes **both the Plasma widget and its native QML
plugin**. No manual extraction or QML import-path configuration is needed.
Run the installation checker as your desktop user, without sudo; it reports
manual/local installations that could shadow the RPM and never deletes them.
Add **USBeeKeeper** through Plasma's **Add Widgets** menu.

Update through your normal Fedora package updater, or run:

```bash
sudo dnf upgrade usbeekeeper
```

The regular `0.1.0` RPM sorts newer than `0.1.0~dev.3`. After upgrading a
loaded native plugin, log out and back in so Plasma loads the updated files.
Normal RPM upgrades and removal retain user settings and physical aliases.

### Separate daemon requirement

`usbeehived` must expose all of the following on the **session D-Bus**:

- Bus name: `org.usbeehive.Devices`
- Object path: `/org/usbeehive/Devices`
- Interface: `org.usbeehive.Devices5`, including `SnapshotJson()` and `Refresh()`

USBeeKeeper does **not** bundle, build, start or modify usbeehive/usbeehived.
The widget uses that daemon exclusively; it does not read sysfs, use libudev
directly or poll. The widget itself does not require root privileges.

## USB inspection and diagnostics

- Device identification using USB descriptors and useful USB database labels,
  while retaining the underlying raw identity.
- USB version and negotiated link speed in the card header; a negotiated link
  rate is not a measured file-transfer throughput.
- Expandable **Device Information** with formatted VID:PID, kernel driver and
  declared maximum USB current when available.
- Capability comparisons, charging information and Alternate Mode diagnostics
  where supplied by the daemon. Warning styling follows the daemon's warning
  flag; being below an advertised capability is not automatically a fault.
- Wrapped technical and diagnostic text, with hover tooltips for capped
  title/subtitle text that still does not fit.
- Manual refresh and automatic hotplug/change updates through D-Bus signals.
  Backend failures are distinguished from a successful empty device list, and
  retained data is marked as potentially out of date after snapshot errors.

**Declared maximum USB current is not live power consumption.** For example,
`500 mA` is the device's declared USB current limit, not a measured current draw
or a wattage reading. Missing data stays hidden rather than being invented.

## Configurable details and Plasma settings

Each widget instance has its own settings:

- **Standard** (default): VID:PID, kernel driver and declared max USB current.
- **Extended**: adds available manufacturer, raw product, class/subclass,
  serial, power source, distinct capable speed, generation, link status and
  relevant Alternate Mode information.
- **Debug**: adds USB database, logical port and companion-port data, connector
  type, hub port usage, committed power, container ID and kernel quirks where
  available.

USB version and negotiated speed are not repeated in the expanded tables.
When USB version is absent from a header, it remains accessible in the
Extended/Debug details, including separate companion-function versions.

Settings also control hub visibility, the topology tree, empty USB-C port
visibility where data is available, and physical-device renaming controls.
Hubs and renaming controls are hidden by default; tree mode requires hubs to
be shown. Detail and renaming-control changes apply without a daemon refresh.

## Topology, companion hubs and physical relationships

The optional tree follows the daemon's logical USB port hierarchy, with
contiguous parent/child subtrees. Logical downstream port numbers do **not**
prove that a connector is physically exposed or removable.

Verified USB 2/USB 3 companion hub functions appear as one presentation hub.
Their underlying logical paths and separate function identities remain
available. Grouping does not rely merely on similar names or a shared vendor.

Bundled declarative profiles cover generic companion hubs and known VIA hub
compositions with integrated audio, or integrated LAN/card-reader functions.
Profiles annotate only members satisfying the complete required signature;
they do not identify a retail product merely from a USB ID or hub child.

**Integrated USB functions remain visible as real USB devices**, with their
own cards and technical identities. Physical metadata augments the logical
topology rather than replacing it. **Unclassified does not mean external.**

### Physical-device aliases

Enable **Show physical device renaming controls** in the widget settings to
assign, rename or clear a friendly physical-device name. The controls default
to off; hiding them does not delete existing aliases. A physical-root alias can
be the tree heading while its logical USB identity remains visible underneath.

Aliases are stored in Plasma configuration, not in the daemon. Portability
depends on available serial/container identity; location-fallback aliases are
tied to the USB attachment location. Ambiguous instance identities do not
share an alias automatically.

## Limitations and testing scope

- The daemon is required, and information depends on what it currently exposes.
  This is not a power meter or a complete USB/Type-C compliance analyzer.
- Unknown physical relationships remain unclassified. Manual local Integrated
  relationship overrides and automatic retail-product identification are not
  implemented.
- Physical profiles cover a small set of known layouts. Contributors can
  normally add a profile with one JSON file, without editing C++ or CMake.
- Installed Fedora COPR operation and updates have been tested; systematic
  alias-persistence testing across installed Plasma session restarts remains
  limited. `plasmoidviewer` uses transient configuration and is not a restart
  persistence test.
- Automated tests cover profiles, model behavior, request sequencing, settings
  and real-plugin QML delegates/layouts. There is no complete fake D-Bus
  integration harness for all daemon-owner transitions.
- Debug details can contain unique hardware identifiers. Review and sanitize
  screenshots or diagnostic reports before sharing them.

## Manual release assets — advanced/secondary

All existing archive types remain available:

| Asset | Purpose |
|---|---|
| `usbeekeeper-plasmoid-v0.1.0.tar.gz` | Plasma applet package; requires the native module below. |
| `usbeekeeper-qml-plugin-v0.1.0-x86_64.tar.gz` | Required native QML module, relative to the Qt 6 QML import root. |
| `whatcable-linux-cli-v0.1.0-x86_64.tar.gz` | Separate legacy WhatCable sysfs/libudev CLI, not the USBeeKeeper frontend. |

For a compatible system, manual installation of both widget components is:

```bash
qt_qml_dir="$(qtpaths6 --query QT_INSTALL_QML)"
sudo tar xzf usbeekeeper-qml-plugin-v0.1.0-x86_64.tar.gz -C "$qt_qml_dir"
tar xzf usbeekeeper-plasmoid-v0.1.0.tar.gz
kpackagetool6 -t Plasma/Applet -i io.github._2crazy4nick.usbeekeeper
```

For an existing manual applet, use `kpackagetool6 -t Plasma/Applet -u
io.github._2crazy4nick.usbeekeeper` instead, and update the native module too.
Do not mix manual copies with the COPR package without checking for conflicts.
Native archives require compatible Qt/KDE libraries; use the Fedora RPM for
Fedora KDE. The legacy CLI is not included in the RPM and is not part of the
validated usbeehive-backed Plasma path.

See the [README](https://github.com/2Crazy4Nick/usbeekeeper-plasma/blob/v0.1.0/README.md),
[Fedora packaging guide](https://github.com/2Crazy4Nick/usbeekeeper-plasma/blob/v0.1.0/packaging/fedora/INSTALL.md)
and [profile contribution guide](https://github.com/2Crazy4Nick/usbeekeeper-plasma/blob/v0.1.0/CONTRIBUTING_PROFILES.md)
for development, manual installation and profile validation instructions.
